## Draft text

This release covers mathematics only; integration of the other subjects is deferred. This change contains source fixes for the Sign in with Apple and in-app purchase failures reported for Xingya 1.0.0 (5) under Guidelines 2.1(a) and 2.1(b). It is not yet evidence of a complete fix in the live review environment.

The fresh physical Face ID attempt at 12:07 produced a server diagnostic of `stage=identity`, `reason=jwks_network`, HTTP 503. The confirmed runtime problem is `redirect: "error"` on the Apple public-key request: [Cloudflare Workers does not support that mode](https://developers.cloudflare.com/workers/runtime-apis/request/), and Request construction throws `TypeError` before sending any network request. An independent curl request to Apple's public-key URL returned HTTP 200 without a redirect. The minimal backend patch now uses `manual` for the JWKS and shared token/revoke requests and continues rejecting 3xx responses without following them. **Patch tests passed and deployment completed at 12:18:21; the current production API retains the fix. Real Apple account creation/sign-in passed on the current iPhone Build 6 at 14:04–14:05; Build 6 was subsequently resubmitted by 14:32 and is now Waiting for Review. This backend patch needs no iOS code change, and Build 6 remains the selected build for this resubmission.**

The 30-minute challenge window, removal of the additional token-age check, retained authorization state across delayed/background callbacks, fresh nonce per attempt, silent cancellation and credential-free failure diagnostics are additional improvements. The live challenge was verified as 1800 seconds after the initial deployment. These improvements retain cryptographic validation and do not extend Apple's authorization-code lifetime. The earlier immediate failures cannot all be attributed to the previous five-minute challenge window. Injected lifecycle tests and silent physical cancellation do not establish successful delayed or background/foreground Apple sign-in.

The previous product-loading path did not retry an empty StoreKit catalog and could show raw purchase errors. Build 6 retries temporary failures and empty results with bounded backoff, requests the catalog again when the Account screen reappears, and offers a localized Retry action. Purchase cancellation returns silently. Successful server entitlement binding is preserved without a redundant second status request turning a completed purchase into a reported failure.

Review paths:

1. Free practice: choose a grade, finish the initial warm-up if shown, then open Home. Free practice and on-device reports do not require an account or subscription.
2. Apple sign-in: Me → Account → Sign in / Create account → Continue with Apple. This is separate from the username/password review-account path.
3. Subscription: sign in with the review account from the controlled App Review Information fields, then open Me → Account → Monthly membership. The product is `com.hanwang.xingya.premium.monthly`. Name and price come from StoreKit. If temporarily unavailable, choose Retry or revisit Account.
4. Complete a Sandbox purchase and confirm active membership after server verification. Canceling should produce no error. To restore, use the original Xingya account and tap Restore purchases.
5. Account → Sync now performs manual server-verified cloud sync. Me → Parent → remote AI parent summary requires valid membership and an actual server response. Local analysis is free and is not proof of a remote result.
6. The membership section includes Manage subscriptions, renewal terms, privacy policy and the Apple Standard EULA. Deleting a Xingya account does not cancel its Apple subscription.
